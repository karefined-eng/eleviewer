# EleViewer Windows Package Manager Release Runbook

Instructions for an AI agent preparing and maintaining EleViewer releases on
GitHub Releases, Windows Package Manager (WinGet), Scoop, and Chocolatey.
Microsoft Store distribution is intentionally out of scope.

## Operating rules

- Read `.agents/AGENTS.md` and this runbook before starting release work.
- Treat the repository's current release workflow, package manifests, and
  platform policies as authoritative if they change after this runbook was
  written. The external documentation links below are the next source of truth.
- This runbook explains the process; it does not authorize a release by itself.
  Push commits, create/push a release tag, publish packages, or submit PRs only
  when the current user request explicitly asks the agent to release or submit.
- Never create, rotate, print, or commit credentials. Use existing authenticated
  GitHub/Chocolatey tooling and repository secrets. Do not put API keys in
  command history, source files, workflow logs, or package manifests.
- Do not enable Azure signing as part of a release. The owner has decided to
  distribute unsigned builds for now. `.github/workflows/build.yml` only runs
  Azure Trusted Signing when `AZURE_TRUSTED_SIGNING_ENABLED` is exactly `true`;
  leave it unset/false unless the owner explicitly changes that decision.
- Do not bypass SmartScreen, browser, antivirus, or operating-system security
  warnings. Unsigned installers may receive warnings; package-manager listing
  does not remove those warnings or establish that a binary is safe.
- Do not silently change installer behavior, package identity, licensing, or
  distribution rights to satisfy a feed. Stop and report the issue if the
  published artifact cannot be used safely and reliably.
- Preserve a release's installer and portable ZIP at their original URLs. Do not
  replace an already published version's bytes; package hashes and client
  caches depend on immutable artifacts.

## Release sequence

For each stable release, work in this order. Do not create a new source version
or tag just to retry a package submission.

1. **Check authorization and existing state.** Confirm that the current request
   authorizes the requested release actions. Inspect `git status`, the current
   branch, tags, latest GitHub Release, open release/package PRs, and the live
   state of each feed. Keep unrelated work and user changes intact.
2. **Prepare one version.** Follow `.agents/AGENTS.md` for version alignment.
   `version.py` is the application version source; the release tag drives the
   workflow's build version. Keep `setup.iss`'s local fallback and the checked-in
   WinGet manifests coherent with the intended version. Do not invent an
   installer hash before the artifact exists. Update changelog and user-facing
   release notes according to the repository's release rules.
3. **Validate before release.** Run the repository's appropriate test/build
   checks and inspect the manifest diffs. Ensure the application version, setup
   version, tag, release notes, and package versions agree. Resolve failures
   before tagging.
4. **Build the release once.** After explicit release authorization, push the
   stable `vX.Y.Z` tag and monitor the `build.yml` run. Do not create the GitHub
   Release or submit WinGet manually while this workflow is running; it already
   does both.
5. **Verify the release assets.** Confirm the workflow succeeded and the
   GitHub Release has the expected setup EXE, portable ZIP, SHA-256 text, and
   generated WinGet installer YAML. Download each asset and independently
   calculate SHA-256. Confirm the expected architecture and that the installer
   and ZIP can be installed/launched as applicable.
6. **Complete WinGet follow-up.** Inspect the PR created or updated by
   `winget-releaser`; follow the WinGet section below. Do not publish duplicate
   submissions.
7. **Publish Scoop and Chocolatey updates.** Follow their sections below only
   after the release artifacts are public and independently verified. If a
   platform's first-time package submission has not been approved or its account
   is not set up, report the blocker instead of implying publication succeeded.
8. **Close the loop.** Verify each platform's public package page/version and
   run the platform's install/update/uninstall checks where possible. Record
   exact URLs, PR numbers, results, and any moderator or owner action still
   needed.

If the GitHub build fails, fix the cause before retrying; do not publish manually
from a partial or locally rebuilt artifact unless the user explicitly approves
that alternative. If a release asset is wrong after publication, stop and
coordinate a correction rather than replacing it silently.

## GitHub Releases

GitHub Releases are the canonical artifact source for every channel:

- Setup installer:
  `https://github.com/karefined-eng/eleviewer/releases/download/v<VERSION>/EleViewer_Setup_v<VERSION>.exe`
- Portable archive:
  `https://github.com/karefined-eng/eleviewer/releases/download/v<VERSION>/EleViewer-Portable.zip`

Before relying on either predictable URL, open the release page and verify the
asset exists. GitHub's tag-based URL is not proof that a release completed.

The current pipeline uses repository contents-write permission to create the
release. Confirm the workflow run and release assets through GitHub; never echo
the contents of any secret. If `WINGET_TOKEN` is absent or invalid, the build
may publish a GitHub Release but fail to submit WinGet. Report this as a
partial release and request the owner to configure the secret through GitHub
repository settings.

## WinGet

**Existing automation:** `.github/workflows/build.yml` submits to WinGet through
`vedantmgoyal2009/winget-releaser@v2`. The release agent's job is to verify the
automation and handle follow-up, not create a second submission.

### Before and during submission

1. Check the package identifier and current upstream state:
   - Repository: <https://github.com/microsoft/winget-pkgs>
   - Identifier: `karefined-eng.EleViewer`
   - Current checked-in manifest source: `winget/`
2. Confirm `WINGET_TOKEN` is available as a GitHub Actions secret without
   exposing its value. If it is missing, do not put a personal token in a
   workflow file; report the missing owner-managed secret.
3. Confirm the tag workflow completed. Inspect its log and the submitted PR.
   Ensure the PR contains only the intended version's manifest files and that
   `PackageVersion`, release URL, architecture, installer type, and SHA-256
   match the public setup EXE.
4. Run `winget validate` on the local manifest set when available, or use the
   repository's current manifest validation tools. Confirm the published URL
   returns the exact installer bytes whose SHA-256 is recorded.
5. Monitor all PR checks and comments. If a reviewer requests a change, make
   the smallest correct manifest fix and update the same PR. Keep one package
   version per PR. Do not resolve/reply to moderator requirements with a
   superficial acknowledgment; supply the requested fix or factual response.
6. Do not claim WinGet is released until the PR is merged and package
   availability can be verified, for example with
   `winget show --id karefined-eng.EleViewer --exact`.

The checked-in YAML is source/template material. The workflow creates a
version-specific installer manifest and calculates the setup EXE's hash from
the build output. Never copy the prior version's hash into a new manifest.
Respect the current WinGet schemas and authoring guide if they change:

- [Create a package manifest](https://learn.microsoft.com/en-us/windows/package-manager/package/manifest)
- [WinGet contributor guide](https://github.com/microsoft/winget-pkgs/blob/master/CONTRIBUTING.md)
- [WinGet first contribution guide](https://github.com/microsoft/winget-pkgs/blob/master/doc/FirstContribution.md)

## Scoop

**Recommended artifact:** the portable ZIP, not the Inno Setup EXE. The ZIP is
approximately 200 MB in the inspected release, so disclose the download size if
the feed asks for it. Scoop manifests require a direct download URL and the
SHA-256 of the ZIP.

### Initial public listing

1. Search Scoop Extras and other relevant buckets for an existing EleViewer
   manifest. Do not create a duplicate or take over a similarly named package
   without coordinating with its maintainer.
2. Scoop's current bucket contribution guide asks contributors to open an issue
   describing a new manifest and wait for maintainer approval before preparing
   a PR. Use the Extras bucket for this GUI desktop app rather than assuming it
   qualifies for Scoop Main.
3. Read the live contribution instructions before creating the issue or PR:
   - [Scoop Extras](https://github.com/ScoopInstaller/Extras)
   - [Scoop bucket contribution guide](https://github.com/ScoopInstaller/.github/blob/main/.github/CONTRIBUTING.md)
   - [App manifest documentation](https://github.com/ScoopInstaller/Scoop/wiki/App-Manifests)
4. After approval, add `bucket/eleviewer.json` to the approved bucket fork.
   Follow its current template, field order, formatting, and CI requirements.
   Include:
   - The exact release version, description, homepage, and verified SPDX
     license identifier.
   - An x64 download URL for
     `EleViewer-Portable.zip` and the SHA-256 of that exact ZIP.
   - A shortcut pointing to
     `EleViewer-Portable/EleViewer.exe`.
   - A `checkver` and matching `autoupdate` rule for the stable GitHub releases
     only if those rules can reliably discover the latest stable tag and
     construct the correct URL.
5. Inspect the ZIP layout before setting `extract_dir` or the shortcut path.
   Test install, launch, update, uninstall, and reset on a clean Windows
   environment. Do not add Scoop `persist` entries until the app's actual
   settings/data locations have been confirmed; incorrect persistence can
   preserve or erase user data unexpectedly.
6. Verify the manifest with the current Scoop validation tools. Submit a PR
   with the title format required by the bucket contribution guide. After
   opening it, add the required `/verify` comment if the current guide still
   requires it. Address CI and maintainer feedback.
7. Once merged, verify the listing and test:
   `scoop bucket add extras`
   `scoop install eleviewer`

### Updating after the initial Scoop listing

For each later stable release, update the same `eleviewer.json` manifest in a
separate upstream PR. Set `version` to the new tag, update the portable ZIP URL
and its freshly calculated SHA-256, and verify that `checkver` and
`autoupdate` still resolve to the exact new asset. Test upgrading an existing
installation and launching the app before submitting. Use the bucket's current
update PR title format, run its verification workflow, add `/verify` when
required, and wait for merge. Never delete and recreate the manifest merely to
force an update.

Use this PowerShell procedure to calculate a portable ZIP checksum from the
published release artifact; do not reuse the setup EXE's checksum:

```powershell
$version = 'X.Y.Z'
$zip = Join-Path $env:TEMP "EleViewer-Portable-$version.zip"
$url = "https://github.com/karefined-eng/eleviewer/releases/download/v$version/EleViewer-Portable.zip"
Invoke-WebRequest -Uri $url -OutFile $zip
(Get-FileHash -LiteralPath $zip -Algorithm SHA256).Hash.ToLowerInvariant()
```

The open-source Scoop Extras bucket is separate from the project repository.
If the agent does not have authority to fork/open an issue or PR there, prepare
the manifest and a proposed PR description locally and report exactly what
owner action remains. Do not claim Scoop availability before the upstream PR
has merged.

## Chocolatey

**Recommended artifact:** wrap the public Inno Setup EXE in a Chocolatey package
that downloads from the stable GitHub Release URL. Do not embed the 130+ MB
installer in the `.nupkg`; downloading the vendor-hosted release with a pinned
SHA-256 keeps the package small and repeatable. Public-feed distribution is
permitted for software the publisher has rights to distribute; EleViewer is
our own GPL-licensed project, but confirm the current LICENSE and feed rules.

### Important installer compatibility gate

The current Inno Setup package uses `PrivilegesRequired=lowest` and writes
per-user registry values, file associations, and PATH configuration. Chocolatey
installs are often run from an elevated terminal. Before publishing, explicitly
test how this installer behaves when run by Chocolatey in both elevated and
non-elevated contexts:

- Which Windows account and install path receive EleViewer?
- Does an elevated Chocolatey install accidentally install only for the
  administrator/SYSTEM context instead of the logged-in user?
- Can Chocolatey find and launch EleViewer after install?
- Does uninstall remove the actual installation and only the values the
  installer created?
- Does upgrade work over the previous version without duplicate PATH entries,
  broken associations, or orphaned files?

Do not submit to the public feed until these cases work safely. If the current
per-user installer cannot be driven reliably by Chocolatey, report the
blocker and recommend fixing installer/package install semantics first; do not
hide the failure with a success-shaped package script.

### Package creation and publication

1. Search the Chocolatey Community Repository for `eleviewer`. If it already
   exists, contact the package maintainer or contribute to that package instead
   of creating a duplicate.
2. Confirm the publisher account is ready to publish, and read the current
   package, distribution-rights, and moderation requirements:
   - [Create Chocolatey packages](https://docs.chocolatey.org/en-us/create/create-packages/)
   - [Quick start](https://docs.chocolatey.org/en-us/create/create-packages-quick-start/)
   - [Community feed moderation](https://docs.chocolatey.org/en-us/community-repository/moderation/)
   - [Package verifier](https://docs.chocolatey.org/en-us/community-repository/moderation/package-verifier/)
3. Use `choco new` to generate an up-to-date package skeleton. Maintain a
   package source in `packaging/chocolatey/` in this repository unless an
   already-approved package source repository is in use. Do not create a
   separate repository without owner approval. The package source needs at
   least:
   - `eleviewer.nuspec`: lowercase package ID `eleviewer`, package version,
     project URL, vendor/author, description, GPL license URL, and release
     notes.
   - `tools/chocolateyInstall.ps1`: download the versioned setup EXE and
     install it with Chocolatey's helper, supplying the verified SHA-256
     checksum and SHA-256 type.
   - `tools/chocolateyUninstall.ps1`: locate the actual EleViewer uninstaller
     and remove it with silent flags. Derive this from the installer behavior
     and test it; do not guess a path or report success when uninstall failed.
   - Optional `README.md` with manual package build/test and release steps.
4. Use the Inno Setup silent options only after testing them against the exact
   released installer. The likely candidate is
   `/VERYSILENT /SUPPRESSMSGBOXES /NORESTART /SP-`, but confirm exit codes,
   relaunch behavior, reboot behavior, and per-user handling. Preserve valid
   installer exit codes where appropriate; do not discard nonzero errors.
5. Build and test in a clean VM using the current Chocolatey guidance:
   - `choco pack`
   - `choco install eleviewer --source . --force`
   - Verify app launch, version, registry and file association behavior.
   - Test upgrade from the preceding version.
   - `choco uninstall eleviewer --yes`
   - Confirm uninstall is complete and user data is preserved.
6. Keep the `.nuspec` and scripts in the encoding required by the current
   Chocolatey package template. Run the current package validator and verifier
   checks where available. New public package versions are moderated; monitor
   the package page and respond to required corrections.
7. Publish with `choco push` to
   `https://push.chocolatey.org/` only after local validation passes and
   explicit release authorization exists. Keep the API key in Chocolatey's
   secure credential mechanism or approved CI secret; never pass a real key as
   a committed literal or echo it to logs.
8. Confirm the public package page shows the intended version and that an
   independent install, upgrade, and uninstall test succeeds before reporting
   Chocolatey complete.

### Updating after the initial Chocolatey listing

For every later stable release, keep the same lowercase `eleviewer` package ID
and update the `.nuspec` version/release notes, the download URL, and the
verified installer SHA-256 in the install script. Review the uninstall script
against any installer behavior changes. Run the full clean-VM install, upgrade,
and uninstall checks, build a new `.nupkg`, then push that exact package
version after explicit authorization. Monitor moderation/verifier results and
do not report the new version as available until its public package page shows
it.

Do not configure automated package publication as part of the first release.
First prove the package scripts and approval path. Automation can be proposed
later using a dedicated repository secret and a reviewable workflow.

## Troubleshooting and reporting

- **No release assets:** inspect the Actions run and stop. Do not publish a
  local build as though it were the canonical release.
- **Hash mismatch:** redownload the public artifact, calculate its SHA-256
  locally, verify the URL and exact file, then update the relevant manifest.
  Never bypass validation or copy another artifact's hash.
- **WinGet PR already exists:** update and monitor the existing PR; don't open
  another PR for the same package version.
- **Scoop contribution not approved:** stop before filing an unrequested PR;
  provide the proposed issue/manifest and ask the repository maintainer through
  the authorized contribution flow.
- **Chocolatey install or uninstall fails:** do not publish. Report the exact
  tested context, commands, exit codes, and cleanup status.
- **Missing credentials or repository permissions:** report which account,
  permission, secret, or maintainer action is needed. Never ask the user to
  paste a token into chat.
- **Unsigned build warning:** disclose it accurately. Do not assert that package
  manager review signs or certifies the EXE.

The final release handoff must list the source tag and release URL, artifact
names and SHA-256 values, workflow result, each platform's live version/URL,
PR numbers, install/update/uninstall validation, and outstanding owner or
moderator actions.
